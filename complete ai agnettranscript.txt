● Good question — a few reasons:

  1. FastAPI handles sync def routes safely already. When a path function is
     plain def (not async def), FastAPI/Starlette automatically runs it in a
     worker thread pool rather than on the event loop. So a sync route doesn't
     block other requests — it's not "wrong," just a different concurrency model
     than async.
  2. The libraries underneath are themselves synchronous. weaviate-client's
     client.collections.* API I used is the sync client (there's a
     _CollectionsAsync variant, but I didn't wire it up), the Groq SDK call is
     groq.Groq(...).chat.completions.create(...) (sync), and
     openrouter_client.py uses httpx.post(...) (sync), not httpx.AsyncClient.
     Marking the route async def while every call inside it is a blocking sync
     call would actually be worse — it would block the single event loop thread
     instead of offloading to the thread pool.
  3. Embedding is CPU-bound, not I/O-bound. sentence-transformers'
     model.encode(...) is a CPU/GPU compute call, not something await helps with
     regardless of which HTTP client style is used — it needs a thread (or
     process) pool either way.
  4. The one place I did use async def is upload_documents, because
     UploadFile.read() in Starlette is a real coroutine (it's backed by anyio's
     async file handling for large uploads) — that one has an actual await to
     make.

  The honest trade-off: if this needed to serve many concurrent requests
  efficiently, the better design would be to swap in the async variants
  (connect_to_weaviate_cloud has an async counterpart, httpx.AsyncClient,
  groq.AsyncGroq) and make the routes genuinely async def throughout. For this
  assignment's scale, sync-with-threadpool is simpler and behaves correctly, so
  I didn't introduce that extra surface area — but it's a reasonable thing to
  revisit if you want the API to look more "production-grade" for the write-up.

  docker-compose up backend
